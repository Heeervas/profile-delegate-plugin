# Detached notification ownership — gated repair plan

**Goal:** No `unknown` completion while a Profile Delegate detached worker is still alive; a finished run has a truthful native ledger completion eligible for delivery. Do not promise exactly-once Discord/Telegram delivery. This plan is separate from test-deslop commit `84edb2885c9b40307c3d25991e1e859874060e04`.

**Incident evidence:** `pd_20260928_060430_aftx6p` registered native `async_delegations.owner_pid=454` (short-lived caller), but its detached worker PID was `33206`. Native `recover_abandoned_delegations()` converted the caller-owned running row to `unknown` and the notice was delivered while the worker lived. The worker later completed `ok`; `_persist_profile_delegate_completion()` treats non-running/non-finalizing rows as already completed, so it cannot correct the delivered `unknown`. The row was read from `/opt/data/state.db` read-only; the reviewer could independently inspect the run artifacts but not that database row or platform record. Preserve this evidence without modifying historical state.

## Hard invariant / decision gate

Before a detached worker can do delegated work or the caller can report accepted dispatch, **one durable, unique native ledger row** for the run must exist with the actual worker PID **and process birth identity**, and recovery must not be able to convert it into an unknown notice while that worker identity is alive. Across caller death, worker death, immediate completion, and restart there must be no interval in which a live unregistered worker is executing, a caller-owned row can be recovered as abandoned, or registration can replace a terminal/delivered row. Once terminal, the row must never return to running. Distinguish one terminal ledger event from at-least-once/ambiguous platform delivery.

The existing native `_persist_dispatch()` is **not** an ownership-transfer API: it uses `INSERT OR REPLACE` with `os.getpid()`, can replace terminal/delivered state, and `get_durable_delegation()` does not expose owner identity. Merely calling it in the child after spawn leaves an unregistered crash window; a read-then-insert or status-file PID change does not satisfy the invariant. **Do not implement those shortcuts.**

**Candidate A, preferred only if a supported native API exists or can be safely introduced under separate Hermes-core authority:** register a paused detached worker with a conditional, transactional native API. Parent spawns paused child and has its PID/birth identity; atomic native operation conditionally inserts exactly once (never replaces) or transfers from an existing caller-owned running row only if its owner identity and `state=running` match. It must reject recovered/terminal/claimed/delivered rows, and expose/verify exact owner identity. Parent acknowledges only after the operation commits and status/identity readback agrees, then releases worker; worker has bounded self-contained behavior if parent dies before release. Native recovery must serialize on that transaction. Obtain approval before modifying `/opt/hermes`; plugin may not write Hermes-owned SQLite rows directly. If no suitable native API is available and core changes are not authorized, **stop with an integration blocker** and a minimal API proposal—not a fake plugin-only fix.

**Candidate B, only if a disposable fault-injection probe proves all invariant cases without native API or direct native SQL:** an alternative plugin-only handshake. Reviewer must inspect the proof before any production-path implementation. A worker-side `_persist_dispatch()` call alone is already rejected. No new plugin-owned durable outbox/bus and no duplicate notice with a new ID to mask the false original.

## Failure-state ownership matrix (must become executable tests)

- Parent dies **before spawn**: parent-owned registered row may become native `unknown`, correctly signaling no worker started; no run acceptance. Do not call it a delegated task success.
- Parent dies **after spawn but before registration**: paused child cannot start delegated work; bounded child self-terminates or safely registers via a proven atomic protocol. No accepted run without durable ledger row. Absence-of-row is a hard stop, not a recoverable-pending claim.
- Registration rejects/fails or worker dies **before release**: child never runs delegated task; caller returns actionable dispatch failure if alive; if caller dead, the design must show how a durable terminal failure is recorded or explicitly narrow the guarantee and report the gap. No false completion. A still-running registered row must converge by recovery when true owner dies.
- Parent dies **after verified registration**: worker owns the ledger with correct birth identity, proceeds or self-terminates according to release protocol; native recovery does not fire while worker is alive. No second registration.
- Worker dies **after release before terminal publication**: recovery eventually emits `unknown` once for genuinely lost task outcome; run status/readback names worker loss rather than success.
- Worker completes and native delivery is pending/claimed/delivered: terminal row is immutable and not re-registered; platform send/ack ambiguity remains explicit. A live parent watcher and detached worker may both see completion, but only one terminal ledger event is persisted.

**Stop rule:** A plan cannot authorize implementing unproven atomic ownership using private Hermes DB writes or `INSERT OR REPLACE`. If the invariant cannot be attained within the approved plugin-only surface, report the core integration requirement, do no production code edit, and seek authority for a separate Hermes-core change and review.
